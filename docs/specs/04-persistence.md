# Persistence, transactions and import

SQLite is the database for V1. Django ORM types map to domain objects; `menus/models.py` is discovery only. Schema evolves via migrations by milestone; do not create all future tables in M0. No schema reset, `flush`, destructive migration or test against real family DB. Keep migrations in Git. All field names in English; technical enum values stable, translated at web edge. Prefer ordinary normalized references where they express invariants; snapshot JSON is intentionally denormalized for history, never blindly store ORM serialization.

JSON codecs encode snapshot/recipe quantities as decimal strings and enums as text, field `schema_version: 1`. Date strings ISO. Explicit field mappings, reject invalid/corrupt payload with controlled error rather than silently filling. Snapshot contains ingredient identity+label, quantity/unit, taste flag, note, preparation, source dish metadata and recipe status. Undo payload holds exact before positions and dish values, eligible version and exact after positions. Never snapshot image or personal seed file path. Add cross-field DB checks where supported; domain validates invariants across rows. Encode all persisted amounts as canonical decimal strings in TEXT or JSON strings, never numeric affinity. Use plain decimal text with exactly three fractional digits, no exponent, and the domain bounds. Validate text in the mapper/domain; check nullability and unit pairing in the DB. Applications must not use floating-point SQL arithmetic.

## Concurrency and atomicity

Use one short SQLite transaction per mutation. Take the Madrid local date after entering it, classify every affected week from this captured Monday, and validate again immediately before a successful time-sensitive return from the transaction. If the Monday changed, roll back all writes and return retryable `503`. A fresh attempt reclassifies the weeks and rejects direct historical writes with `403`. Catalogue and recipe changes retry the entire operation from fresh state and refresh only still-editable weeks. The final successful clock check is the logical time boundary for an admitted write. Never hold a transaction open for UI confirmation.

Use aggregate compare-and-swap (`UPDATE ... WHERE pk = ... AND version = expected`) before replacing dependent rows. Zero rows means `409`. SQLite cannot rely on row locks from `select_for_update`. A busy/locked or stale SQLite snapshot aborts the whole transaction and maps to retryable `503`; classify and retry from a fresh transaction, never reuse old projections or automatically resubmit stale input. No-op requests still validate tokens and editability and do not increment versions. Use sorted week keys for atomic fan-out. An assignment and a catalogue or recipe write that race must agree with a serial outcome: either the assignment sees the new dish state, or propagation refreshes the newly assigned slot. Failure leaves all affected roots, slots and overlays unchanged.

Use short read transactions for multi-query views that combine a menu, its slots and shopping overlay. Use exactly one shopping token `(menu_version, overlay_version_or_zero)`. Compare both components inside each shopping mutation. A first effective write inserts the overlay root under a unique week constraint; a competing attempt loses with `409` or a retryable `503`. Increment only the menu version when only the menu or generated data changes, and the overlay version when persisted overlay data changes. Never materialize an empty overlay from a GET or an unmodified command. Related menu or effective recipe changes reconcile existing overlays in the same transaction.

A virtual editable week submits version 0. Its first assignment or skip reserves the unique Monday before reading write dependencies, then saves the mutation in the same transaction. A conflict or replay of version 0 returns 409 without a second write. A failed mutation rolls back the root and all slots. Dish and manual-product creation use a server-issued opaque UUID carried by the form through errors and network retries. Hash canonical validated input with operation and scope using SHA-256 over deterministic UTF-8 JSON, with sorted keys and set-like lists, exact decimal strings and explicit nulls. A supplied token must be a valid UUID. An identical replay returns the original created ID without creating a row or applying another write, even if the week version advanced or the original manual row was deleted. If deleted or now historical, report the original outcome with a safe link to its list and do not recreate it. Reuse with a changed payload or scope returns `409`. Check an existing receipt before time/version checks for a new write; for a new token enforce all guards. A uniqueness race rolls back the attempted create and checks the receipt outside the failed transaction. A rolled-back attempt consumes no token. Until success or a known rollback, retry the same token and input. A new intended creation gets a new token.

Undo and both affected slots are persisted together. Upon a related snapshot change clear undo; on unrelated refresh rebase its eligible version after preserving the pair's before/after values.

## Historical projection and upgrades

Assign `shopping_projection_version=1` when the first week schema is introduced in M2. At M7, preexisting weeks use version 1 as well. Past reads use exact frozen slot and recipe values plus any saved overlays; no backfill from the live catalogue and no database writes on GET. Use stable ingredient keys, exact values, display-label selection, row order, coverage logic and versioned snapshot decoding. Missing saved recipe or overlay remains missing.

Any later change affecting historical generated keys, amounts, displayed data or deterministic order gets a new projector version. Keep the previous projector and compatible decoders available for historical rows. Upgrade editable weeks only through an explicit, tested migration or mutation that respects rollover, reconciles overlays, and changes the version atomically. Do not rewrite past weeks or silently interpret them using the newest rules. Upgrade tests compare the semantic DTO before and after for a frozen past fixture, including shopping rows, order, warnings, manual products, checks and orphans.

## M0 upgrade and import

Keep `menus/migrations/0001_initial.py`. Add a forward migration that seeds 13 categories, maps existing primary and secondary strings to stable keys, and preserves dish IDs, names, preferences, and flags. Add version 1 and unarchived defaults. Use staged data and schema operations so constraints follow validation. Stop and roll back on unknown labels, primary/secondary repetition or other invalid legacy values, including an exhausted automatic ID range. No reseeding, deletion, source rewriting or destructive reset. Verify automatic IDs after explicit IDs. Test fresh install and a populated synthetic upgrade, plus rollback on an unknown category. Compare fields and memberships before and after.

Keep `python manage.py import_catalogue /path/to/private.csv` as the canonical CLI. Accept UTF-8 with optional BOM, standard CSV quoting and CRLF/LF. Require the exact set of unique header names `id,name_ca,primary_category,secondary_categories,meal_preference,special_occasion,recipe_status,image_status` in any order. Secondary categories are blank or comma-separated labels in the CSV field, using standard quoting for multiple entries. Trim secondary category whitespace as the existing adapter does. Preserve dish names, validate nonblank names within the supported domain length, and validate primary and secondary labels against the seed vocabulary. Reject duplicate/invalid IDs, zero records, malformed records, repeated categories and primary repetition. IDs are positive ASCII base-10 integers within signed SQLite range, reserving its maximum value for at least one subsequent automatic ID. Validate strict `lunch|dinner|both`, `true|false` and pending recipe status. Accept and discard image status. If preflight detects a source discrepancy, stop and report only row, field and error code. The reviewed private copy already matches the vocabulary and needs no spelling edit.

Parse the entire file before writes. In one write transaction compare all imported fields for each ID, insert only missing IDs, and leave identical existing and unrelated rows untouched. Preserve archive state and recipes. Any conflict or write failure rolls back the whole import. Identical reruns leave versions and counts unchanged, except the returned unchanged count. Treat duplicate inserts by a concurrent importer as conflict or reload from a fresh transaction. No datasource values in error output. Keep the existing opt-in fidelity route, extending it against the upgraded schema, and report NOT RUN when private input is unavailable.

## Verification and privacy

Use synthetic data and an explicit absolute disposable `DJANGO_DB_PATH` for file-backed QA and verification. Never point migration rehearsals or failure injection at the family database. Follow the [operations contract](08-operations.md) for artifact isolation and private source handling.

# Configuration, privacy and operations

## Environment

Existing Python/Django skeleton and Linux server. Use Python version compatible with installed Django 5.2 line (project target Python 3.12 if available; do not modify system Python). `python3 -m venv .venv`, `.venv/bin/python -m pip install -r requirements.txt`, `.venv/bin/python manage.py check`, migrations and tests. Keep dependencies minimal and pin supported versions deliberately in requirements after checking actual environment. Do not run arbitrary shell installers or use sudo without approval. No system service edits, no Nextcloud changes, no router/firewall edits without owner. Configure `LANGUAGE_CODE='ca'`, `TIME_ZONE='Europe/Madrid'`, timezone support, no Django admin URL; no login/session user feature. Keep framework contrib dependencies only if required for chosen messages/CSRF etc; default auth not exposed. No CSRF exemption on writes.

Require explicit production secret, hosts and absolute database path. DEBUG defaults false. Safe dev/test settings may supply isolated defaults only in explicit dev/test mode. For persistent QA, verify the absolute `DJANGO_DB_PATH` under a fresh `mktemp -d` directory before migrating or importing. Django does not automatically load .env. Use placeholders in .env.example. Bind only to the owner-selected trusted household interface and port. Verify actual IPv4 and IPv6 reachability from an allowed household device and denied guest/untrusted paths before release. Inspect router forwards, tunnels and Docker effective port exposure. CSRF and host checks are required but cannot enforce the network boundary. Configuration or network remediation requires owner approval.

## Development and deployment

Use one dedicated Compose service with a persistent directory for SQLite and its sidecars, no unrelated container integration, and explicit interface and port binding. Use Gunicorn for WSGI and WhiteNoise for collected project static files with local assets only. Add only those serving dependencies at M8, pin compatible versions and verify them in the isolated build. Run migrations as a one-off before starting the app. Django runserver is for disposable QA. Expose a minimal /healthz with 200 for reachable DB and 503 otherwise, with no data or paths. Document validated Compose, migration, startup, health check and rollback commands. Release still requires owner authorization and verified reachability.

## Data governance

Private CSV, database and sidecar files, backup directories, env/secrets, legacy private mockups and real-data screenshots, imported recipes or menus, logs and local paths never versioned. `.gitignore` covers `/PLATOS_57.csv`, `/data/`, `/backups/`, `*.sqlite3`, `*.sqlite3-*`, `.env`, `.env.*` except `.env.example`, `.venv/`, caches, `.idea/`, private UX (`/private-ux/`), local logs (`/logs/`, `*.log`, `*.log.*`), and local analysis, progress, and review reports (see the root ignore rules). Ignore patterns are not a security boundary for already tracked files: verify index/history with `git ls-files`, `git status`, `git diff --cached` and inspect content before push; use synthetic examples. Do not copy old UX bundle into public docs. Do not echo source records, credentials or actual config into review output or generated docs. The replacement synthetic `docs/ux/` design may be versioned as documentation. No images in the application; design documentation is not app code or runtime assets.

Build from an allowlisted context staged outside the source tree. Include only the reviewed app source, dependency manifest and build files. Exclude private CSV, databases and sidecars, backups, secrets, local virtual environments, Git metadata, documentation previews, logs and real screenshots. Inspect the context and final image with synthetic marker files to verify exclusions. Apply equivalent allowlists to published archives and verify Git tracked files, staged changes and history before any publication. Keep private data in owner-restricted directories outside tracked paths. Export only synthetic QA evidence.

## Backup/restore

Use SQLite online backup API or stop only this app for consistent file copy (do not copy live SQLite file without WAL consistency). Document command taking explicit DB and backup paths outside repo, protect owner file permissions, verify `PRAGMA integrity_check` on restored copy; never overwrite production during rehearsal. Restore to separate DB, run Django checks/migrations after version compatibility check, compare synthetic row counts and representative data, then owner-approved production switch if needed. Document rollback caution: code rollback after incompatible migration may require matching backup. Production backups are not automated by this package without owner request; backup schedule optional later. Ensure app restart preserves state. Test actual import and E2E on disposable databases before using real data.
